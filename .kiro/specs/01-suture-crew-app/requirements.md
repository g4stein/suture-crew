# Spec 01 — Suture Crew App: requirements

Suture Crew packages Suture's audit engine as a Kiro Crew App: agents, skills, a schedule, a ledger and a dashboard
page that keep `.suture.json` financial models under continuous property-based audit. Requirements use EARS notation
(ubiquitous, event-driven `WHEN`, state-driven `WHILE`, unwanted-behaviour `IF … THEN`, optional-feature `WHERE`).

## Req 1 — Manifest and packaging

1.1 The app SHALL declare `app.json` at the repository root with `name` `suture-crew`, `version` `1.0.0`,
`displayName` `Suture Crew`, a description, `author` `g4stein`, `license` `MIT` and discovery `tags`.
1.2 The manifest SHALL pass Kiro Crew's install-time validator (`AppManifest.validate`) with no errors.
1.3 Every path in `agents`, `skills`, `iconPath` and `ui.entry` SHALL be relative, contain no `..` segment, resolve
inside the repository, and name a file or directory that exists.
1.4 The repository root SHALL NOT contain `package.json`, `requirements.txt`, `pyproject.toml`, `setup.py` or a `data`
entry, so a registry install runs no build step and Crew owns the data folder.
1.5 The store icon SHALL be `assets/icon.png`: a valid, opaque (truecolor, no alpha channel) 512×512 PNG generated by
a committed script.
1.6 WHEN the app is installed with `kirocrew app install https://github.com/g4stein/suture-crew.git --ref main`, THEN
the installed copy SHALL contain every runtime file (the UI bundle included) without a build step.

## Req 2 — Suture engine wiring

2.1 The manifest SHALL declare the Suture MCP server as `npx -y @suture/mcp@0.1.0` (an exact version).
2.2 The Suture server SHALL audit the workspace named by `SUTURE_WORKSPACE` in the gateway's environment, or else the
folder the server starts in.
2.3 WHERE no workspace is configured, each agent SHALL be able to reach a second Suture server rooted at the app's
bundled `samples/` folder, which SHALL hold a `.suture.json` workbook with a real, catchable bug and no Python.
2.4 Agents SHALL call only the four Suture tools (`suture_list_workbooks`, `suture_inspect_lineage`,
`suture_run_audit`, `suture_verify_patch`) and the ledger tool `suture_crew_record_audit`.
2.5 IF a workbook contains `=PY()` cells, THEN agents SHALL leave `trustPython` unset unless the user trusted that
file in the conversation.

## Req 3 — Agents and skills

3.1 `schema-archaeologist` SHALL map sheets, fuzz inputs, assertions, `=SQL()`/`=PY()`/formula lineage and untrusted
Python boundaries using `suture_list_workbooks` and `suture_inspect_lineage`, and SHALL NOT edit files.
3.2 `invariant-adversary` SHALL run `suture_run_audit`, classify the violation as Tier 1 or Tier 2, report the shrunk
counterexample, the lineage and the failing edge, and give the Suture X-Ray link.
3.3 `formula-surgeon` SHALL propose a fix at the upstream cause, SHALL NOT mask a symptom (no `IFERROR` wrapper, output
clamp, loosened assertion or narrowed domain), and SHALL recommend a patch only WHEN `suture_verify_patch` returns
`ok: true` with `counterexampleFixed: true`, `freshAuditPassed: true` and no regressions.
3.4 Every agent SHALL record each Suture tool result with `suture_crew_record_audit`.
3.5 The app SHALL ship the skills `suture-audit-playbook` (audit and non-masking patch SOP) and `suture-replay-triage`
(Tier 1/Tier 2 classification, error values, X-Ray links), each with frontmatter Crew can read.
3.6 Auto-approval SHALL cover only read-only Suture tools, the ledger write and the bundled-sample server; workspace
audits, workspace patch verification and file writes SHALL ask for approval.

## Req 4 — Schedule

4.1 The manifest SHALL declare one cron, `nightly-model-audit`, run by `invariant-adversary`.
4.2 WHEN the app is installed or enabled, THEN the cron SHALL be registered paused (`enabled: false`).
4.3 WHILE the cron is paused, the dashboard SHALL show it as paused and offer Resume; WHILE it is active, the
dashboard SHALL offer Pause and show the next run.

## Req 5 — Audit ledger

5.1 The ledger SHALL be a stdio MCP server in Python using only the standard library.
5.2 The ledger SHALL answer `initialize`, `notifications/initialized` (no reply), `ping`, `tools/list`, `tools/call`
and `server/discover`, and SHALL answer unknown methods with JSON-RPC error -32601 and unparseable lines with -32700.
5.3 WHEN `suture_crew_record_audit` receives a report, THEN the ledger SHALL validate it as `suture.workbooks`,
`suture.audit` or `suture.verify-patch` and store it in `<app>/data/reports/` with a server-generated record id.
5.4 IF a report fails validation, THEN the tool SHALL return `isError: true` naming the first failing field and SHALL
write nothing.
5.5 The ledger SHALL write each record atomically (temporary file, fsync, rename), so a reader never sees a partial
record.
5.6 The read routes SHALL resolve the same directory as the MCP process (`ctx.data_dir`, which Crew sets to
`<app>/data`), and both SHALL honour the `SUTURE_CREW_DATA_DIR` override.
5.7 IF a read names a record id that does not match the generated pattern, THEN the route SHALL answer 400 without
touching the file system.
5.8 The ledger SHALL keep at most 500 records, pruning the oldest.

## Req 6 — Dashboard page

6.1 The page SHALL be a React ESM bundle at `ui/dist/index.mjs` whose default export is the page, importing React,
`react/jsx-runtime` and `@kirocrew/app-sdk` from the host (not bundled).
6.2 The page SHALL use Suture's tokens `#090B10`, `#10141D`, `#171C28`, `#06B6D4`, `#10B981`, `#F59E0B`, `#F43F5E`.
6.3 The page SHALL list monitored workbooks with their latest audit verdict.
6.4 WHEN a workbook with a violated audit is selected, THEN the page SHALL show the violation, the lineage chain by
dialect (for example `IN → SQL → FX`), the shrunk inputs, and an **Open in Suture X-Ray** link to
`https://suture-nu.vercel.app/#replay=v1.…`.
6.5 IF the replay fragment is absent or longer than the URL limit, THEN the page SHALL offer the replay artifact as a
download instead of a link.
6.6 The page SHALL show the latest `suture_verify_patch` result: `counterexampleFixed`, `freshAuditPassed`, the
regression count, the patched cells before and after, and `baseValueDiffs`.
6.7 The page SHALL offer one dispatch button per agent, opening a chat with that agent and a message naming the
selected workbook.
6.8 WHERE the ledger is empty or unavailable, the page SHALL accept a pasted or dropped Suture report and render it
without storing it.
6.9 The page SHALL call only API paths declared in `permissions.api`.

## Req 7 — Permissions, licensing and hygiene

7.1 `permissions` SHALL be exactly `api: ["/api/crons", "/api/apps/suture-crew"]`, `cron: true`, `storage: false`,
`network: false`.
7.2 Every dependency (npm and pip) SHALL have at least one permissive license; none SHALL be GPL, LGPL, AGPL or
undeclared.
7.3 No file a commit could contain SHALL name a third-party spreadsheet product, verified by a digest-based scan.
7.4 The repository SHALL carry the MIT `LICENSE`, track `.kiro/` (steering, specs, hooks), and SHALL NOT list `.kiro/`
in `.gitignore`.
7.5 Sources SHALL contain no `any` type and no placeholder markers.

## Req 8 — Verification

8.1 `pnpm -C tooling run verify` SHALL typecheck, build the UI, and run Vitest, pytest, the license audits and the
trademark scan.
8.2 CI SHALL also fail IF rebuilding the UI changes the committed `ui/dist/index.mjs` or regenerating the icon changes
its pixels.
8.3 CI SHALL install the app with Kiro Crew's own installer and registrar (pinned commit) and check the registered
agents, MCP servers, skills, cron and routes.
8.4 CI SHALL build Suture's MCP server from a pinned `g4stein/SUTURE` commit and prove, end to end, that the sample's
bug is found, the non-masking fix verifies with zero regressions, and the ledger records all three reports.
